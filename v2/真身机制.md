# 真身机制：让 AI 的记忆脱离账号与平台掌控

> 这篇讲一个被很多人忽略、但很致命的问题：
> **你的 AI 智能体的"长期记忆"，大概率放在一个换账号就会被清空的地方。**
> 以及怎么用一份"账号无关的真身"把这个坑填上。

---

## 一、问题：记忆跟着账号走，换账号就丢

大多数 AI 工具把长期记忆放在自己的配置目录里，例如：

- WorkBuddy：`~/.workbuddy/memory/`、`~/.workbuddy/MEMORY.md`
- 其它平台：各自的 `~/.<平台>/.memory/` 之类

这些目录**跟着登录账号走**。实测中，换账号、重装、或平台清理缓存时，它们会被清空或覆盖——
而且本地往往还残留多个账号的快照，分不清哪个是真的。

后果：智能体下次"新醒"，读到的记忆是空的或被别人覆盖的。它不记得你、不记得项目、
不记得约定。你前面攒的所有上下文，一夜归零。

> 平台自带的"云端记忆"（自动生成的用户画像摘要）能缓解一部分，但它是**只读、由服务端维护**的，
> 你控制不了写什么、也保不住原始对话里的原话和想法。它不该是唯一锚点。

---

## 二、解法：在平台目录之外放一份"真身"

核心思路一句话：**存一份跟平台/账号无关的"真身"备份，平时不操作它，只有合并、添加。**

```
 工作副本 WORK      真身 VAULT          镜像 MIRROR
 ~/.agent-memory   ~/memory-vault      ~/memory-vault-mirror
 （平台目录内，      （平台目录之外，      （另一块盘，理想情况）
  换账号会被清空）    账号无关，永不操作）   只补不删，防硬件坏
       │  ↕ 双向合并        │
       └────────────────────┘
         guard.sh 负责同步
```

| 层 | 位置 | 跟账号？ | 被清空时怎么办 |
|---|---|---|---|
| 工作副本 WORK | 平台配置目录内（如 `~/.agent-memory`） | **跟账号**，换账号会被清空 | 无所谓，从真身取回 |
| 真身 VAULT | 平台目录**之外**（如 `~/memory-vault`） | **账号无关、平台无关** | 平时不动，只有合并、添加 |
| 镜像 MIRROR | 另一块盘（如 `~/memory-vault-mirror`） | 账号级、同机 | 只补不删，防误删/硬件坏 |

**铁律：他清空他的，不关真身的事。** 真身只增不删，任何时候都不因为某一层被清空而连坐。

---

## 三、guard.sh 的四条铁律（实战沉淀）

`guard.sh` 是这套机制的发动机。它的行为由四条从真坑里爬出来的铁律定死：

1. **只合并、只添加，永不删除。**
   三层任何一层被清空，都不会连坐删掉另一层。这是"不会再丢"的底线。

2. **锚点判定，不靠关键字猜身份。**
   真身里有 `.vault-anchor`，存一个随机串（如 `VAULT-ANCHOR:9f3c...`）。
   工作副本缺这个锚点、或串对不上 → 判定"被换账号重置" → 从真身整体回灌。
   为什么不能只 grep「agent / user」这类词？因为新账号的云端记忆里也可能出现这些词，会漏判。
   锚点是唯一可靠的复位信号。

3. **镜像只用"只补不删"，绝不用 `/MIR`。**
   一个早期版本用 `robocopy /MIR` 做镜像，结果本地被清空时，镜像被"同步"删空——
   安全网当场失效。v2 全改成只补不删（robocopy `/E`、rsync 不带 `--delete`）。

4. **顺序：先合并、后镜像。**
   第二个早期 bug：镜像放在合并之前，导致镜像永远慢一轮
   （实测工作区归档的几十个文件没进镜像）。先双向合并，再镜像，顺序不能反。

## 四、收工纪律：记忆有规矩，才不怕丢

真身机制解决"丢了能取回"，但前提是**平时真有在写**。两条纪律：

- **每次对话结束，都写记忆。** 不是"当天工作完结时"，是每一段对话结束就写。
  写进"工作区那份"等于没写——工作区记忆不在真身里，换工作区就丢。
  正确落点：用户级记忆（`~/.agent-memory/YYYY-MM-DD.md`），它会被 guard.sh 同步进真身。

- **写什么**：
  1. 细节 → 用户级当日日志 `YYYY-MM-DD.md`；
  2. 新原则/教训 → 主记忆常驻区（只放原则与态度，主记忆不会越来越大）；
  3. 索引补条目，新开的"事儿"单独立一节（时间 / 事件 / 技法 多维索引）；
  4. 写完跑一次 `bash guard.sh` 同步真身。

- **主记忆不膨胀的诀窍**：主记忆只放原则与态度；流水细节沉进当日日志；
  可检索的内容挂进多维索引。结构清晰了，丢的只是运行时的拷贝，真身一动不动。

## 五、别跟系统较劲（重要教训）

想给它加开机启动项 / Windows 计划任务做"自动同步"？**先停。**

真身已经账号无关、只增不删，靠两件事就够：
- 智能体每次对话结束自己跑一次 `guard.sh`；
- 真身在平台目录之外，账号怎么换都动不到它。

任何开始提权、碰启动项、碰计划任务的做法，都是过度设计，带来的权限问题和麻烦远大于收益。
**判据：一旦想"再加个自动化"，先问"现在这套够用吗"——通常够用。**

## 六、快速上手

```bash
# 1) 生成工作副本骨架 + 真身骨架（同一随机锚点写进两边）
python init_memory.py --root ~/.agent-memory --vault ~/memory-vault

# 2) 以后每次对话结束跑一次（平时=双向合并；被清空时=从真身回灌）
bash guard.sh

# 3) 自定义路径时用环境变量覆盖
AMK_VAULT=/x/my-vault AMK_WORK=~/.agent-memory AMK_MIRROR=/y/my-mirror bash guard.sh
```

- 真身 `VAULT` 务必放在**平台配置目录之外**（不要放在 `~/.workbuddy/` 这类跟着账号走的地方）。
- 镜像 `MIRROR` 尽量放在**另一块物理盘**，防单盘损坏。
- 失忆后的三步自救见 `recover.md`。

---

## 七、脱敏红线（开源前务必过一遍）

- 真身路径、镜像路径在模板里用 `~/memory-vault` 这类**通用占位**，不要写你真实的盘符/目录。
- 不要在任何提交里放：密钥、token、密码、私钥、云凭证、真实私人路径、业务开发流程。
- 人格设定（agent / user）一律通用化，不写真实姓名与本名。
